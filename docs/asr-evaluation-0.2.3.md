# 中文与日语语音识别方案评估（2026-11-04）

当前结论：中文增加 SenseVoice-Small 本地可选方案，日语暂保留 Whisper medium 为比较基线，均不自动替换现有配置。用户报告普通话整句也识错或漏字，因此评测重点是完整句子、金额日期和分段遗漏，而非仅补充术语。0.2.3 在“本地设置 → 语音转文字引擎”中提供选择，保存后重新打开 App 生效。四段合成录音不能代替自然会议准确率，后续还须在真实中日会议录音、参考文字和翻译模型并发条件下验收。

## 中日对照实测

使用本机已有 Tingting、Eddy 中文及 Kyoko、Eddy 日语声音离线合成四段录音，各模型输入完全相同，锁定输入语言。下表为模型预热后第二次整段转写耗时，包含 Whisper 词时间计算，不包含翻译、首字等待和首轮加载；SenseVoice 此表尚未加入后续的 Silero 语音活动检测开销。测试不是实时播放：持续回放的调度耗时另列。该次机器负载明显高于下方早先的短句测试，不能视作固定性能保证。

| 样本 | 时长 | SenseVoice int8 | Whisper medium 8bit | Whisper turbo 8bit |
| --- | ---: | ---: | ---: | ---: |
| 中文长句、字幕与历史记录 | 22.48 秒 | 0.47 秒；内容相符 | 7.18 秒；内容基本相符，输出繁体 | 8.78 秒；内容相符 |
| 中文金额、日期、项目名称 | 12.29 秒 | 0.24 秒；仍有“覆盖”“暂定”“方便”等识错 | 7.22 秒；被旧置信度过滤整句丢弃，已定位并修复 | 8.98 秒；仍有多处同音字错误 |
| 日语长句、左右双栏 | 12.07 秒 | 0.23 秒；开头“皆さん”有误 | 6.20 秒；内容相符 | 8.58 秒；内容相符 |
| 日语金额、日期、截止时间 | 10.86 秒 | 0.22 秒；内容相符，数字写为阿拉伯数字 | 7.22 秒；内容相符，数字写为阿拉伯数字 | 9.81 秒；内容相符，数字写为阿拉伯数字 |

原始结果和参考文字见 [对照结果 JSON](evaluations/asr-bilingual-0.2.3.json)。其中原始 CER 只执行 NFKC、大小写及标点空格归一，不转换简繁、日语汉字/假名或书面数字，所以“十一月”与“11月”也记为差异；不能直接用该数字宣称词义准确率。medium 的整句拒绝发生在修复前：原始 decoder 实际产生了文字，但 `no_speech_prob=0.868`。修复后，仅当独立语音检测确认有人讲话时允许保留这类输出，仍检查平均解码概率和重复率；检测到无语音则不显示。未连接语音检测文件时保留原有保守过滤，不放宽阈值。

SenseVoice 直接转写纯静音及随机噪声时曾输出“我”。现已要求其同时连接 Silero 语音活动检测权重；静音、两档随机噪声、100Hz 嗡声均未输出字幕，四段中日语音仍能识别。它不是免错识别器：日本语切片回放中也出现“訳文→約文”和边界漏字，故不作为日语默认替换方案。

最终包内另用 Whisper medium + Silero 回放中文金额样本，确认不再整句拒绝，但“预算”“下周三”等仍有识错或遗漏，不能称为中文精度问题已解决。日语分段回放仍出现“訳文→役分”，翻译也随原文错误偏离。由此保留两种引擎供同一录音对比，不能仅凭整段短测结果宣称日语识别已经合格。

分段/分人验证使用两种声音“甲→乙→甲”：中文 59.25 秒、日语 37.00 秒。首次不含 VAD 的 SenseVoice 中文全流程耗时 9.50 秒；日语 32.21 秒。两次均生成两个匿名声纹编号，内容按三个连续发言段保留；确认换人的位置有约数秒误差，边界附近可能混入另一人的少量文字。该声纹权重面向中文，日语仅做这次合成声音工程检查，未验证自然日语多人会议。旧 medium 回放曾耗时 353.77 秒并漏掉较多内容，说明当前负载下它不能保证实时。不要把这些离线全速回放数据称为端到端字幕延迟。

## 本地模型连接

已下载评测用权重并校验后连接到用户当前指定的模型目录 `/path/to/models/asr/sensevoice`，未提交模型或音频到 GitHub，未改动 Ollama 或默认识别引擎。SenseVoice 默认位置为 `~/Library/Application Support/LocalMeetingInterpreter/models/asr/sensevoice`，需要 `model.int8.onnx`、`tokens.txt`、`silero_vad.onnx`；自定义模型根目录后对应 `asr/sensevoice` 子目录，或设置 `MEETING_INTERPRETER_SENSEVOICE_MODEL`。运行时不会下载文件。Whisper 若发现该 Silero 文件，也会用它辅助抑制噪声及避免错误的整句拒绝。

## 本机实际对比

M3、16GB，已有本地 8bit 权重，固定中文，无网络识别。测试音频为一段 6.60 秒的合成普通话，内容为“大家好，今天我们讨论本地会议翻译，请在下周三之前完成测试”。下表是第二次调用耗时，不包含首次加载，亦非端到端字幕延迟。

| 模型 | 普通转写 | 带词时间信息 | 该样本识别结果 |
| --- | ---: | ---: | --- |
| Whisper medium 8bit | 0.93 秒 | 1.51 秒 | 与参考文字相符 |
| Whisper large-v3-turbo 8bit | 1.10 秒 | 2.29 秒 | 与参考文字相符 |

这一个干净、合成、较短的样本不支持计算真实会议准确率，也不能证明两个模型精度相同。turbo 的现有缓存使用 `model.safetensors` 文件名，而安装的 mlx-whisper 寻找 `weights.safetensors`；本次只在临时目录建立别名完成测试，没有更改原模型权重。

还进行了约 59 秒、两种本地合成声音“甲→乙→甲”的回放，用来发现和修复长发言丢字、提示词回灌、分段截断及声纹标号问题。它是工程验证，不代表自然多人会议、远场噪声或重叠发言已经验收。原始音频与模型均不提交仓库。

## 候选方案

| 方案 | 适用方向 | 接入与验证重点 |
| --- | --- | --- |
| 当前 Whisper medium / turbo（MLX） | 保持现有本地中日英链路 | 先修复窗口覆盖和提示词回灌；八秒内音频上下文修订、完整词边界提交，避免把程序问题误判成模型能力问题 |
| SenseVoice-Small（ONNX） | 中文为主的会议，兼顾中英日 | 已接入并实测上列中日样本，配独立语音检测。原模型离线推理，本项目采用可修订的音频窗口，不能称为原生流式模型。时间来自 CTC token 起点，用相邻起点作区间边界；数字规范化若不能与 token 对应，则不使用重叠裁切，避免错误对齐 |
| Qwen3-ASR-0.6B（MLX） | 本机低内存、多语言候选 | 支持中文、英文、日文；MLX-Audio 有 Apple Silicon 实现。需验证量化精度、推理耗时和翻译模型同时常驻时的内存，未在本机下载或测速 |
| Qwen3-ASR-1.7B（MLX） | 准确率优先的候选 | 模型作者报告更强的识别能力；16GB 与翻译模型同时使用时须测内存和持续实时率，不能仅凭参数规模下结论 |

Qwen 官方 Python 方案的原生流式接口目前依赖 vLLM，不能直接套用为本机 M3 方案。MLX-Audio 的实际增量生成、语言指定和时间对齐接口需要单独适配；附带的 ForcedAligner 是额外模型，不能在资源评估时忽略。

## 后续评测标准

分别统计普通话、日语、会议术语、人名、金额日期、中日/中英混说和远场噪声。中日使用字符错误率（CER），同时提供数字及简繁等价归一前后结果，另列关键名称与数字的正确率、漏句比例、静音错误字幕次数。至少记录首字延时、修订完成延时、持续运行速度以及 ASR 与 Ollama 同时运行的内存；使用不同于调参样本的录音验收。语义润色不能替代原音证据，也不应让翻译模型任意改写原文。
